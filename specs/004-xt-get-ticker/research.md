## 研究任务

### 1. 三角套利路径发现算法

**问题**: 如何高效发现所有可能的三角套利路径（A→B→C→A）？

**研究发现**:
- **算法选择**: 使用图遍历算法（深度优先搜索 DFS）
  - 将交易对构建为有向图：节点=货币，边=交易对
  - 从每个基础货币（如 USDT）开始 DFS，深度限制为 3
  - 时间复杂度: O(V×E²)，V=货币数量，E=交易对数量
  - 对于 500 个交易对约 100 个货币，复杂度约 100×500²=25M 操作，<100ms

**决策**: **图遍历 + 深度限制**
**理由**:
- 符合 <1s 全市场扫描要求（NFR-001）
- 简单易实现，循环复杂度 <10
- 无需外部图算法库（符合依赖最小化原则）

**备选方案**:
- ❌ 广度优先搜索（BFS）：内存占用更高，不符合 <100MB 限制
- ❌ 预计算所有路径：需要持久化存储，不符合 N/A Storage 要求

### 2. 收益率计算公式

**问题**: 如何准确计算三角套利的预期收益率（扣除手续费）？

**研究发现**:
- **公式**: `最终金额 = 初始金额 × price1 × price2 × price3 × (1 - fee)³`
- **收益率**: `(最终金额 - 初始金额) / 初始金额 × 100%`
- **手续费**: 每个交易环节扣除 fee（默认 0.1% = 0.001）
- **买价/卖价选择**:
  - A→B: 使用 B/A 的 ask 价（买入 B）
  - B→C: 使用 C/B 的 ask 价（买入 C）
  - C→A: 使用 C/A 的 bid 价（卖出 C 换回 A）

**决策**: **链式乘法 + 3 次手续费扣除**
**理由**:
- 准确反映实际交易成本（买价高于卖价）
- 计算复杂度 O(1)，符合 <10ms 要求
- 避免浮点精度问题（使用 Decimal 类型）

**备选方案**:
- ❌ 只扣除一次手续费：不准确，高估收益率
- ❌ 忽略买卖价差：过于乐观，实际套利机会更少

### 3. 彩色控制台输出库选择

**问题**: colorama vs rich，哪个更适合套利机会打印？

**对比研究**:

| 特性 | colorama | rich |
|------|----------|------|
| 安装大小 | 25KB | 500KB |
| 依赖数量 | 0 | 3 (commonmark, pygments, typing-extensions) |
| 彩色输出 | ✅ ANSI 转义码 | ✅ 高级样式 |
| 表格格式 | ❌ 需手动实现 | ✅ 内置 Table |
| 性能 | 快（纯 ANSI）| 慢（需渲染） |
| 跨平台 | ✅ Win/Linux/Mac | ✅ Win/Linux/Mac |

**决策**: **rich**
**理由**:
- 内置表格格式化，方便展示多条套利机会（FR-011）
- 性能影响可忽略（输出频率 <1次/秒，非性能瓶颈）
- 更好的用户体验（彩色 + 表格 > 纯 ANSI 颜色）
- 依赖增加可接受（3 个小型库，总体积 <1MB）

**备选方案**:
- ❌ colorama：需手动实现表格格式化，增加代码复杂度
- ❌ 纯 print：无彩色区分，用户体验差

### 4. 异步价格数据处理策略

**问题**: 如何高效处理批量价格数据（get_ticker() 返回所有市场）？

**研究发现**:
- **Feature 003 接口**: `async get_ticker(symbols: list[str] | None) -> list[Ticker]`
  - symbols=None 返回所有市场价格
  - 单次调用获取所有数据，无需并发请求
- **数据流**:
  1. `await exchange.get_ticker(None)` → 获取所有价格（<2s, NFR）
  2. 过滤无效数据（bid > ask, price ≤ 0）
  3. 构建交易对图（货币→交易对映射）
  4. DFS 发现所有三角路径
  5. 并发计算收益率（asyncio.gather）
  6. 筛选 + 排序 + 输出

**决策**: **单次批量获取 + 流式处理 + 并发计算**
**理由**:
- 符合 Batching Strategy（减少 API 调用）
- 流式处理避免缓存所有价格（符合内存限制）
- 并发计算收益率加速处理（asyncio.gather）

**备选方案**:
- ❌ 逐个查询价格：API 调用过多，违反批量策略
- ❌ 同步计算收益率：速度慢，不符合性能目标

### 5. 性能优化策略

**问题**: 如何确保 <1s 全市场扫描和 <100MB 内存使用？

**优化策略**:

#### 5.1 内存优化
- **流式处理**: 不缓存历史价格，仅保留当前扫描数据
- **图结构**: 使用 dict[str, set[str]] 表示货币邻接表（轻量级）
- **路径表示**: 使用 tuple 而非 list（不可变，内存更小）
- **及时释放**: 扫描完成后清空图结构和价格数据

**预估内存**:
- 500 个 Ticker 对象：500 × 200B = 100KB
- 图结构（100 货币）：100 × 10 邻居 × 50B = 50KB
- 路径列表（最多 1000 条）：1000 × 300B = 300KB
- **总计**: <1MB（远低于 100MB 限制）

#### 5.2 计算优化
- **路径发现**: DFS 深度限制为 3，避免无限递归
- **早期剪枝**: 遇到无效价格立即跳过，不继续搜索
- **并发计算**: 使用 asyncio.gather 并发计算所有路径收益率
- **排序优化**: 只保留前 N 条高收益机会（Top-K 算法）

**预估性能**:
- 路径发现: 25M 操作 × 1ns = 25ms
- 收益率计算: 1000 路径 × 10µs = 10ms（并发）
- 排序: 1000 × log(1000) = 10ms
- **总计**: ~50ms（符合 <1s 要求）

**决策**: **流式 + 图结构 + 并发计算 + 早期剪枝**
**理由**:
- 符合所有性能约束（NFR-001, NFR-002, NFR-003）
- 无需外部优化库（符合依赖最小化）
- 代码简洁（循环复杂度 <10）

## 关键发现总结

1. **三角套利算法**: 图遍历 + DFS（深度3）+ 早期剪枝
2. **收益率计算**: 链式乘法 + 3 次手续费扣除 + Decimal 类型

4. **异步策略**: 单次批量获取 + 流式处理 + 并发计算
5. **性能优化**: 内存 <1MB，计算 <50ms，符合所有性能目标
